# Android 心跳测试包

这个分支提供一个与原版并存的测试 APK。测试包的应用 ID 是 `com.alyssa.polaris.debug`，显示名称为 **Polaris 心跳测试**；原版仍使用自己的应用 ID 和数据目录。新安装的测试包会从空白数据开始，需要在测试包里使用 Polaris 自己的导入流程导入备份。

这是基于当前公开源码构建的定制测试版。公开源码的 Android 版本元数据是 `1.0`，无法据此证明它与原作者发布的 `1.0.83` 安装包逐文件一致。

## 从 GitHub 获取 APK

在本仓库的 **Actions → Android heartbeat test APK** 中打开当前心跳分支的构建。此工作流在 `codex/polaris-heartbeat…` 或 `heartbeat/…` 分支推送时运行，也可以通过 **Run workflow** 手动运行。

只有全部检查与 Android 构建成功之后，构建页才会出现 `polaris-heartbeat-debug-…` artifact。下载并解压后包含：

- `polaris-heartbeat-debug.apk`
- `polaris-heartbeat-debug.apk.sha256`

工作流只打包仓库源码与依赖，不需要模型 API 密钥，也不会读取手机里的聊天、图片或人设。真实模型配置应在测试包中按 Polaris 原有方式填写。

## 本地构建

需要：

- Node.js 24 与 npm。
- JDK 21。虽然部分应用代码写的是 Java 17，Capacitor 8 的 Android 模块使用 Java 21。
- Android SDK：`platform-tools`、`platforms;android-36`、`build-tools;35.0.0`。
- 项目锁定的 Gradle 8.14.3 与 Android Gradle Plugin 8.13.0，由 Gradle Wrapper 下载。

先设置 `ANDROID_HOME`（或 `ANDROID_SDK_ROOT`）为 SDK 所在目录，然后在项目根目录运行：

```bash
bash scripts/build-heartbeat-android.sh
```

脚本会安装锁定依赖、构建网页、同步 Capacitor、编译 debug APK，最后将安装包和校验和放进 `artifacts/`。`--prepared` 仅跳过依赖安装、网页构建和 Capacitor 同步，适用于 CI 已执行这些步骤的情况。

## 测试包更新与数据

测试包使用 debug 签名，只用于个人测试。工作流使用明确指定的 `.heartbeat-signing/debug.keystore` 路径生成与缓存专用测试 debug 密钥，Gradle 通过 `POLARIS_HEARTBEAT_DEBUG_KEYSTORE` 使用同一文件。此前默认路径缓存没有实际保存密钥，旧构建的签名仍各不相同；从本次修正开始，缓存可用时后续构建沿用同一签名。最早一份 APK 的临时密钥未保留，因此本次修复包不保证能覆盖最早版本；缓存丢失时也可能改变签名。请始终保留原版和原版完整备份，在测试包里产生了需要保留的新聊天后，也应导出备份。

若后续需要长期覆盖更新，应另行采用同一份专用签名密钥；密钥不应提交到仓库。当前工作流没有使用原作者的签名，也没有配置任何发布签名凭据。

构建成功证明代码可以打包，不代表已经在真实 Android 设备上验证了后台唤醒、系统权限、断网恢复和导入数据后的行为。安装后的设备验证需要分别进行。

## 这一版能验证什么

心跳直接使用 Polaris 原有协作者、模型绑定、会话、跨会话召回、素材与工具流程，不要求重新填写另一套人设，也不会把已有聊天上传到新后台。

1. 在测试版导入备份，先确认人设、聊天和素材完整。
2. 打开主动消息规则，选定同一协作者与会话，选择“一次性预约”，安排几分钟后的时间。
3. 选择“安静做事”或“主动聊天”；勾选“允许协作者自行安排下一次唤醒”会开启主动消息工具。
4. 提示词可以写：“看看我们最近还有什么想继续的事，有值得做的就做一点，也可以不行动。结合实际情况决定下次何时醒来。”
5. 保持应用运行，观察会话里的实际工具证据及规则里的下一次时间。安静模式保留工作记录和模型可回看的最终备注，不显示普通聊天气泡或发送回复通知。

一次性预约执行前会先保存已领取状态，完成后不会自动重复。开启自主续约时，模型可以更新同一条规则为新的具体时间，也可以不预约。每条自主规则最近 24 小时最多启动 12 次，每次活动最多 5 分钟；实际调用费用还取决于原有模型和工具往返次数。新用户消息会中止正在进行的心跳。

**后台能力的明确边界：本测试版的模型和工具仍由 Polaris 应用运行时执行。关闭或被系统结束后，不会继续调用模型或翻相册。**普通聊天规则可以安排系统到点通知；应用仍运行时可直接执行，运行时已暂停则需恢复应用才能继续。到点提醒不代表模型已经执行，真正保存的回复另行通知。安静规则不安排这种外部提醒。实现退出应用后持续执行，还需要独立常驻执行端或经过验证的原生后台运行时，不属于这个 APK 已完成的能力。

原版和测试版使用不同应用 ID。原版的聊天、密钥和数据目录不会被测试版直接读写；需要通过现有导入流程导入你自己保存的备份。请先用备份副本在测试版核对导入结果，再决定是否用于日常聊天。

## 安卓导入长记录修复与诊断

针对“第一次只恢复对话、后续域失败；重试后所有域失败”的报告，已发现一个可单独验证的风险：每域提交前的校验会读取已导入的完整聊天行，Android CursorWindow 可能拒绝过大的 JSON 行。修复让单值 LocalData/会话元数据读取使用 SQLiteStatement.simpleQueryForString，避免该窗口限制，不改变数据格式或指针发布与验证顺序。只有 SQLiteDoneException 被视为缺行，其他读取错误仍向上传播。

Android instrumentation 回归使用合成的数 MB 中文与 emoji JSON，确认旧 Cursor 读取在受限窗口下抛出 SQLiteBlobTooBigException，修复路径逐字读回并可再次读回；同时检查后续域、空查询、普通目录查询、会话元数据和数据库故障传播。CI 成功表示这些测试已在安卓模拟器执行，不代表已经确认用户手机上的全部导入问题已消失。

部分导入弹窗对已识别的读取窗口、SQL 合约和验证错误显示固定诊断代码，不展示原始记录或密钥。若实际备份仍无法完整导入，应根据新的结果进一步诊断；不可用关闭校验、清空原版或丢弃源记录的方式绕过失败。

补充共享导入回归：合成长聊天在模拟读取窗口限制下，首次仅 chat 提交、第二次零域提交；恢复完整单值读取后，同一 ZIP 连续两次完整恢复全部七域，且源消息正文逐字一致。该测试不使用私人备份。

## 房间域恢复旧备份的修复

显式导入备份时，collection 的对象内容可合法早于本地同 ID 的预置卡片或较新编辑。原导入计划沿用了旧内容时间作为行写入版本，因此仓库会拒绝这一域，其他六域可正常恢复。本修复仅在显式导入边界将完整 collection 行的信封更新时间设置为本次恢复时间；内容中的原始时间、正文、ID 与普通写入的防过期校验均保留。

新增回归覆盖：较旧备份替换较新本地卡片，完整七域恢复，内容时间不变，重复恢复成功；而晚于导入开始的新记录仍受到保护。该测试复现了单独房间域失败的一类原因，实际手机结果仍需确认。版本冲突与重复记录也会显示固定诊断代码，不输出记录标识或正文。

## 分段气泡与自主开关

协作者回复按 Markdown 块在界面上拆成段落气泡。单个段落内的换行仍属于同一气泡，标题与其后的块放在一起，列表、表格、代码、数学和富卡片保持块结构。仅改变显示，聊天源记录、消息 ID、工具归属及模型上下文保持完整；复制、编辑、重试和整条回复朗读仍使用原消息。

自主续约改用现有的小型可访问开关，避免通用输入框样式拉伸复选框。已使用合成内容在 390 像素 iframe 视口检查分段样式、窄屏布局和开关状态切换。截图中的私人主题和聊天未用于公开测试数据。

用户已验证一次性预约在重新打开 Polaris 后继续加载；这仍是前台/恢复执行路径的证据，不是独立后台执行器已经完成的证据。


## 新备份文档往返与诊断

测试版新备份恢复时出现单独 document 域 IMPORT_VALIDATION；后续固定分类诊断确认四份协作者记忆文档缺正文。现已复现普通备份按钮遗漏未打开记忆正文的入口缺陷，详见下一节。新回归使用合成的长中文、emoji、协作者记忆文档和工作区文档，导入后直接从持久化源导出（不先打开正文），再恢复到空库并重复恢复，逐字比对正文。

这条回归确定暴露了另一个问题：JSZip 对字符串分块 UTF-8 编码时可能拆开 UTF-16 代理对；原生 ZIP 文本桥接同样独立编码每一段。网页 ZIP 现在先将 JSON 整体编码为 UTF-8 字节；原生桥接则保持代理对在同一段内。该修复可以避免新导出的 emoji 变成替代字符，不会凭空恢复旧备份中已经缺失或损坏的正文。

导入继续保留完整性校验和失败域的旧行、旧指针。在建立 document 导入计划前，对正文缺失或长度不足输出固定分类及数量（记忆、工作区、孤立正文），不含内容、标题、ID 或密钥。其他投影验证失败会保留实际验证类别，不再一律丢成“缺少验证报告”。这些诊断用于后续定位设备报告，不是放宽验证。仅使用合成数据编写回归；用户备份未上传到仓库。

## 普通备份按钮的记忆正文修复与定向补回

设备的新诊断为四份协作者记忆文档缺正文、长度不足零、工作区零。已找到普通备份按钮的另一条入口：`prepareCompleteExportSnapshot` 提供了内存协作者目录，使导出绕过持久化读取；该入口原先只加载工作区正文，未加载协作者记忆正文。未打开且未暂存的记忆资料因此可能只导出目录。新增入口回归先失败，补上记忆正文加载后通过；任何记忆正文读取失败现在会终止完整备份，不能生成缺正文却称完整的 ZIP。本地文件与 WebDAV 共用此修复。

“从备份补回记忆文档”是独立的本地恢复操作：从原版完整备份中读取记忆正文，只为当前仍声明、尚未加载且长度大于零的资料补回缺失行。要求协作者/文档 ID、内容版本时间和声明长度精确匹配。已有完整正文、删除标记、当前变化的资料均不覆盖，不修改聊天、人设、房间或设置；不导入备份中的其他域。写入仍由文档仓库和文档串行队列执行，故障读取不能当作缺行。存在未迁移的旧格式正文或不可信文档行时停止操作，保留数据等待核对。

合成回归覆盖四份长中文/emoji 资料经普通备份入口导出、空文档库定向补回、逐字读取、重复操作无写入、实际当前聊天及目录保持不变、已有更新正文保护、删除标记保护、版本不匹配/源正文缺失、重复源记录拒绝，以及读取失败零写入。没有使用或上传私人备份。


## 普通备份入口加载记忆正文与定向补回

普通“导出当前完整备份”按钮调用 prepareCompleteExportSnapshot，再把界面快照传给共享 ZIP 导出器。原入口只加载 workspaceReferenceDocs 正文，未加载 persona.memory.referenceDocs；因此，即使持久化正文完整，未打开的记忆目录也可能只以空 content/contentLoaded=false 进入快照，而共享导出器不会再次读取这些正文。之前仅测试持久化导出入口不足以覆盖此路径。

修复在生成普通导出快照时同时加载协作者记忆正文和工作区正文，读取失败就停止完整备份，不包装缺正文的目录。此入口由本地文件与 WebDAV 共用。真实入口回归使用四份未打开的合成长中文与 emoji 文档，核对 ZIP 中四份正文逐字完整，再从该 ZIP 向空文档库补回并读回一致；两个新增入口测试先在旧逻辑失败，再在修复后通过。

已经缺正文的新备份无法凭空恢复正文。在“备份与恢复”新增“从备份补回记忆文档”：选择仍含正文的原版 Polaris 完整备份，仅尝试为当前未加载、缺少正文的记忆目录补回同 ID、同版本时间、同正文长度的源内容。操作只读取备份的协作者目录与记忆正文文件，不导入聊天或设置；只通过现有文档数据所有者追加缺失正文及更新其文档元数据，不覆盖已存在的完整正文，不复活显式删除行，不更改协作者目录、人设、聊天、房间和设置。

读故障不被视为缺行；不完整源、重复源记录和未匹配版本不用于写入。提交前在文档串行队列中再次检查现有正文及当前目录是否变化。尚有旧格式正文或未完整读取的文档库时停止补回，避免抢占旧存储。合成回归覆盖四文档补回、真实新聊天保持、重复补回无写入、较新正文保留、版本不符、源正文缺失、重复源、读错误、目录变化及显式删除保留。手机上的四份文档仍需用户选择原版备份后核实结果。


## 回复等待与应用内跨页更新

设备报告为界面仍能正常滑动，但普通回复和心跳的文字浮现慢，且用户观察到进入对话后才出现。源码确认主动触发器位于全局应用运行层，没有要求进入目标对话的条件；仍不能仅凭此确定手机上这次延迟的全部原因。

修复三个可单独验证的环节。第一，普通回复请求可复用 60 秒内的 MCP 目录；同配置、超时和重试策略的并发发现共用一次请求。显式目录刷新默认仍直接刷新，身份凭据和工具启用配置变化会使缓存失效；工具执行结果不被缓存或伪造，服务不可用时仍可能等待原配置的超时。第二，从加载历史/记忆开始就标记正在处理；模型回复占位提前到外部工具发现之前显示。准备过程中可以取消，取消不继续请求模型，也不会中断其他请求共享的只读目录发现。第三，流式文字原先依赖 requestAnimationFrame 才写入内存会话，现在增加 100 毫秒后备定时器，绘制回调停滞时也能写入已收到的内容；绘制恢复不重复提交，结束时清理两类调度。

心跳也会启动现有分段耗时记录，只记录时间与数量，不记录聊天内容或完整会话 ID。普通聊天和心跳共用上述回复路径。新增合成回归覆盖：近期缓存命中/过期/强制刷新/凭据变化/工具禁用与包含禁用项的调用、并发目录只读发现合并、MCP 尚未返回时已显示占位并可取消、历史未加载时可取消、绘制回调停止与恢复、在目标会话未打开且应用仍运行时心跳可调用回复/保存消息/发布通知而不导航至会话。

全量通过不代表手机上的全部延迟已确认消失。后备定时器依赖 JavaScript 仍在运行，应用关闭、WebView 被系统暂停或进程被结束后的独立后台执行仍未实现；外部模型和 MCP 服务本身的网络耗时也不会因此消失。设备需要分别验证留在规则页等待和普通回复显示。

## 已保存回复的跨页预览与系统通知

设备后续已确认：普通回复及时显示；留在主动规则页、不进入聊天时，心跳也能执行、保存正文并自主修改下次预约。模型选择了比测试提示更晚的时间，这证明自主续约发生，不等于严格三分钟续约已通过。用户仍需进入聊天才能查看正文，且系统仅显示旧的预约提醒。

本次把回复通知接到原模型运行链路的已提交正文边界：完整一轮可见正文先经现有聊天所有者保存，再发布应用内预览并尝试系统通知，不再等待所有后续工具执行和续约轮次结束。流式片段与纯工具占位不触发通知。原先用消息数量截取新回复，改为排除运行前的消息 ID 并核对本次提交 ID，避免历史压缩或卸载后漏选正文。每次心跳最多尝试一次系统回复通知；后续正文只刷新同一应用内预览，避免重复响铃。通知发送失败或权限被拒绝时仍保留正文预览，异步发送完成不会复活已关闭的提示或把新预览退回旧内容。
